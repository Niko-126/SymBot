# 评测标准 v1.0（可复跑）

> 这是一把尺。换项目、换版本、加新参评方，照着跑一遍就能得到可比的分，不靠印象。
> 立标时间：2026-11-02 ｜ 首次基线数据在文末第十节。

---

## 〇、给不想看细节的人

如果你只是想知道「怎么判断一个 AI 机器人好不好」，记住三句话：

1. **分两把尺量**：「它有多强」和「你能不能装上」是两件完全不同的事，不能合成一个分。
2. **每个分都要有证据**：能指到具体文件或命令输出，否则这个分不算。
3. **别信自报数字**：作者说「20 分钟装好」，那是他机器上什么都装好了的口径。

下面是可以直接照着执行的标准。要跑分就从第一节开始读。

---

## 一、两条口径，别混用

| 口径 | 问的问题 | 维度数 | 满分 | 用途 |
|---|---|---|---|---|
| **A · 全功能** | 它**能做到什么**，做得多深 | 14 | 140 | 选型、技术评审、竞品分析 |
| **B · 小白易用性** | 一个不写代码的人**能不能上手** | 10 | 100 | 推荐给非技术用户、决定「先装哪个」 |

两套口径共用：独有能力矩阵、token 计量规程、仿真测试规程、产出与命名、复跑 SOP。

**铁律**：两条口径必须**分开跑、分开出报告**。不要合成一个总分——
「功能强但装不上」和「好装但没灵魂」是两种完全不同的结论，混在一起就废了。

---

## 二、通用纪律

1. **只读参评项目**。审计前后各跑一次 `git status`，报告里写清楚「参评仓库干净」。
2. **一个项目一个评审员**，并行跑；评审员之间**互相看不到对方分数**，避免抄分、避免对齐全场。
3. **不许编数字**。跑不起来就写 `not_run` / `blocked: <真实报错首行>`，这一项按静态证据给分。
4. **每个分数必须有证据**：文件行号或命令输出原文。没有证据的判断直接删掉。
5. **对自家项目同样苛刻**。自家如果有「少一步就废」的坑，必须写进卡点清单。
6. **功能缺失要标 `missing`**，不要用「正在做/规划中」糊过去。

## 三、口径 A：全功能（14 维 × 0–10 = 140）

### 3.1 维度定义

| # | 维度 | 看什么 |
|---|---|---|
| 1 | 部署与运行门槛 | 依赖、一键启动、容器支持、Windows 原生支持 |
| 2 | 消息平台覆盖 | QQ / 微信 / TG / Discord / 飞书 / Slack / Web…按适配器个数与成熟度 |
| 3 | 人格与角色扮演 | 人设结构、长期一致性、多角色切换 |
| 4 | 记忆系统 | 短/长期、按人分区、召回、遗忘、可编辑 |
| 5 | 关系与情感模型 | 好感/信任/厌恶等数值、阶段、恋人/家人/否决等社会规则 |
| 6 | 主动性与生活感 | 主动外发、日程、念头、身体状态、夜间静默 |
| 7 | 社交执行力 | 主动联系第三方、点歌翻唱、语音条、表情包、群管理动作 |
| 8 | 语音与多模态 | 音色克隆、语音识别、图像理解、视频/音乐处理 |
| 9 | 工具与插件生态 | 插件市场、MCP、工具环、权限 |
| 10 | WebUI 完整度 | 面板、可视化、可操作性（不是「有个页面」就算） |
| 11 | 工程质量 | 测试数量与可运行性、CI、lint、类型、模块边界 |
| 12 | 数据与隐私 | 本地优先、无云依赖、数据隔离、导出/迁移 |
| 13 | 文档与可维护性 | README、架构文档、贡献指南、更新日志 |
| 14 | 性能与资源占用 | 冷启动、单轮延迟、内存/显存、并发 |

### 3.2 打分锚点

| 分 | 含义 |
|---|---|
| **10** | 能直接上生产，有测试兜底，有文档，边界情况想过 |
| **7–9** | 完整可用，少数缺口（缺测试 / 缺某种场景 / 平台少一个） |
| **4–6** | 有主体实现，边角要自己补，或完全没有测试 |
| **1–3** | 只有雏形；或只有硬编码版本；或必须大量自己写 |
| **0** | 完全没有（此时状态必须是 `missing`） |

### 3.3 独有能力矩阵

某一家有、另一家没有的能力，缺失方对应位置写「未实现」，并登记：

```json
{"feature": "按人分区记忆 + 关系四维 + 冷归档还原", "owner": "某家",
 "others": ["另三家"]}
```

**规矩**：只登记「结构性差异」，不登记「参数多少」这种程度差异。
每条必须能指到对方仓库里「搜不到」的事实（例如全仓搜索命中 0）。

## 四、口径 B：小白易用性（10 维 × 0–10 = 100）

### 4.1 只走最省事的那条路

项目同时提供容器 / 安装包 / 一键脚本 / 源码安装时，**只走最省事那条**；
另一条最多一句「还有更麻烦的路」。

### 4.2 维度定义

| # | 维度 | 看什么 |
|---|---|---|
| 1 | 安装方式 | 有没有安装包 / 一键脚本；要不要先自己装运行时 |
| 2 | 前置依赖 | 运行时 / 数据库 / 编译工具 / 另一个软件，**越少越好** |
| 3 | 步骤数量 | 从「下载完」到「发出第一条消息」要几步（≤3 步 = 10） |
| 4 | 图形界面 | 能不能不碰命令行、不碰配置文件 |
| 5 | 配置难度 | 表单填写 / 改 YAML / 改 JSON / 改代码 |
| 6 | 默认可用 | 不填 key、不改配置，能不能先跑起来 |
| 7 | 出错可诊断 | 报错能不能看懂、有没有自检、日志在哪 |
| 8 | 文档友好 | 中文、有截图、有「下一步点哪」 |
| 9 | 恢复与升级 | 备份、回滚、重装、清数据 |
| 10 | 首次跑通耗时 | ≤10 分钟 = 10；>2 小时 = 1 |

### 4.3 步骤计数规则

- 一次**需要人动手的决策/点击/输入** = 1 步；纯等待不算。
- 每步标 `need_cli`（要不要敲命令）和 `need_doc`（不看文档会不会）。
- **「装别人的软件」也各算 1 步**（装运行时、装宿主程序、扫码登录…都算）。
- 只统计到「发出第一条消息」。想接 QQ 群聊的额外步骤单独记，不混进主步骤数。

### 4.4 卡点必须写真名

每条至少给：在哪一步、技术上是怎么回事、**人会在哪儿懵**。
**静默失败要单独标出来**——界面正常、脚本不报错、但实际不通。这类是小白杀手。

### 4.5 打分锚点（这一节是口径 B 的核心）

缺了它，不同的人打出来的分不可比——**10 分必须是同一种「省事」**。

**安装方式**

| 分 | 长什么样 |
|---|---|
| 10 | 官方安装包，双击下一步到底 |
| 7 | 有官方一键脚本，但要敲一行命令 |
| 4 | 只能源码装：自己装运行时 + 装依赖 |
| 1 | 连安装说明都要翻 issue 才能拼出来 |

**前置依赖**

| 分 | 长什么样 |
|---|---|
| 10 | 装完那个包，什么都不用再装 |
| 7 | 再装一个「人人都有」的东西（浏览器级别） |
| 4 | 要自己装运行时 + 一个 API key |
| 1 | 要装 3 个以上外部软件，且版本互相咬 |

**步骤数量**

| 分 | 长什么样 |
|---|---|
| 10 | ≤3 步 |
| 7 | 4–6 步 |
| 4 | 7–10 步 |
| 1 | ≥11 步，且中途要查文档才知道下一步 |

**图形界面**

| 分 | 长什么样 |
|---|---|
| 10 | 全程点鼠标，黑窗口一次都不出现 |
| 7 | 有面板，但首启要敲一次命令 |
| 4 | 有面板，配置仍要手改文本文件 |
| 1 | 全程命令行，或压根没有面板 |

**配置难度**

| 分 | 长什么样 |
|---|---|
| 10 | 面板里填表：选模板 + 粘贴 key + 保存 |
| 7 | 面板里填表，但有几项必须去别处抄 |
| 4 | 手改 JSON/YAML，字段名看不懂，改错不报错 |
| 1 | 要改代码，或要理解内部数据流才能填对 |

**默认可用**

| 分 | 长什么样 |
|---|---|
| 10 | 装完直接能对话（自带可用模型/离线兜底） |
| 7 | 不填 key 也能看到界面、点得动，会明确提示去填 |
| 4 | 不填 key 界面正常但**完全无响应且不报错**（静默） |
| 1 | 不填 key 连启动都不行 |

**出错可诊断**

| 分 | 长什么样 |
|---|---|
| 10 | 报错中文、指到具体文件；有自检一键体检 |
| 7 | 报错能看懂，日志有固定路径，FAQ 覆盖常见坑 |
| 4 | 报错是英文堆栈或空对象，日志位置要自己找 |
| 1 | 失败完全静默 |

**文档友好**

| 分 | 长什么样 |
|---|---|
| 10 | 中文、有截图、按步骤写「点哪个/填什么」，含常见问题 |
| 7 | 中文文档完整，但没有截图或少量过时 |
| 4 | 只有英文或只有 README，快速开始默认你已装好前置 |
| 1 | 文档与代码不符，或要读代码才知道怎么跑 |

**恢复与升级**

| 分 | 长什么样 |
|---|---|
| 10 | 界面里能备份/恢复/升级；一键清数据；重装不留垃圾 |
| 7 | 有脚本或文档写清备份路径与升级方式 |
| 4 | 升级要自己拉代码或覆盖文件；数据要自己找 |
| 1 | 升级即毁配置；或不知道数据存在哪 |

**首次跑通耗时**

| 分 | 长什么样 |
|---|---|
| 10 | ≤10 分钟 |
| 7 | 10–30 分钟 |
| 4 | 30–90 分钟 |
| 1 | >2 小时，或当天跑不通 |

**一致性校验**：打完后自检两件事——
① 步骤数与耗时不能矛盾（12 步却写 5 分钟 = 错）；
② 「默认可用」给 10 分的项目，不该在卡点里出现「没填 key 没反应」。

### 4.6 首次跑通时间怎么给

- 定义：**从「下载完」到「发出第一条消息」**，按「完全不会电脑的人」估。
- 必须给区间，并写清依据（文档步骤数 / 实测的某一段）。
- **不许照抄项目自报的「20 分钟」**——作者的时间是「前置全装好」的口径。
- 拆分建议：装运行时 + 装宿体 + 注册/扫码 + 配置，加总后再给区间。

### 4.7 口径 B 的证据要求（比 A 更硬）

| 要什么 | 怎么算合格 |
|---|---|
| 一键脚本 | 必须指到**真实存在的文件**；搜不到就写空并说明「文档说有但仓库里没有」 |
| 前置依赖 | 全部列出，包括「另一个软件的某个版本」；漏一个 = 不合格 |
| 步骤 | 每步都要标「要不要敲命令」「不看文档会不会」 |
| 卡点 | ≥2 条真实卡点，带位置；**静默失败**必须单独标出 |
| 评分 | 每维都要证据，指到文档行号或脚本行号 |
| token | 口径 B 也要测（同五场景 + 组件拆解） |

### 4.8 三个常见误判

1. **把「文档写得好」当「能跑通」**：文档里 6 步，前提是宿主软件已装好、框架已登录。要按「从零」重数。
2. **把「有界面」当「不用配置」**：面板里仍要手填端口 token 白名单，那一栏不认识照样卡死。
3. **把「作者 20 分钟」当「小白 20 分钟」**：作者手里有编好的环境、知道日志在哪。小白连「日志在哪」都是第 7 步。

## 五、Token 计量规程（两口径都要）

### 5.1 两个数一起记，缺一不可

| 数 | 怎么来 | 意义 |
|---|---|---|
| 离线估算 | 用通用分词器离线数 | 可复现、零成本，但**对中文偏差极大** |
| 真实计数 | 把同一段文本真发给模型，读接口返回的用量 | 精确值，就是真实计费口径 |

实测偏差范围：**-14% ~ +73%**（同一份中文提示词，离线估算可能高估 73%）。所以**不能只报估算值**。

### 5.2 五个固定场景（不许增删）

| 场景 | 输入 |
|---|---|
| `chat` | 「今天有点累，不太想说话。」 |
| `group` | 群聊三人，最后一句 @她「你昨天说的那个游戏叫啥」 |
| `recall` | 「我上次跟你说我妈住院的事，你还记得吗」 |
| `tool` | 「帮我查一下今天的汇率」 |
| `love` | 「我喜欢你」 |

### 5.3 三条硬规矩

1. **用来计量的提示词必须落盘存档**，别人能复算；不许只贴一个数字。
2. **同一段只调一次真实接口**（工具有哈希缓存，重复调会命中缓存）。
3. **三口径对账**：离线估算 / 真实计数 / 项目自己接口返回的用量——三个数都要写；
   真实值与接口自报值偏差应小于 1%，超了说明提示词抓错了。

### 5.4 组件拆解

把一次 `chat` 的提示词按构建来源拆块，每块给 token 数与来源位置：
`系统常驻 / 人格卡 / 记忆注入 / 工具 schema / 历史对话 / 本轮用户消息`。
**拆块之和应约等于整份**（差值是分隔符和空行，要说明）。

## 六、仿真测试规程（口径 A 的硬证据）

1. **先找它自己声明的测试命令**（package.json scripts / Makefile / pyproject / pytest.ini / scripts 目录）。
2. 按顺序尝试，记录：命令 / 退出码 / 通过数 / 失败数 / 备注。
3. 依赖缺失导致的失败**不算项目失败**，写 `blocked: <真实报错首行>`。
4. 附加要跑的：lint、类型检查、CI 配置是否存在。
5. 结论里要区分三种「绿」：

| 类型 | 含义 |
|---|---|
| **真绿** | 全量跑通 |
| **降级绿** | 靠 mock 或兜底才过，必须写明 |
| **假绿** | 只跑了子集或跳过一堆 |

## 七、评分合成

- 口径 A：14 维直接相加（满分 140）；并列时看「关系」+「记忆」谁高（这两项最难伪装）。
- 口径 B：10 维直接相加（满分 100）；并列时看谁的步骤更少。
- **必须同时给「能力分」和「易用分」**，并在报告里一句话说清二者冲突。
- 不允许为了好看做加权调和；权重留给读者自己。

## 九、快速复跑 SOP

1. **准备**：把参评项目克隆到独立目录。
2. **改标准**（只在换维度/换场景时）：改了要记版本。
3. **派评审**：每个项目一个独立评审，只读参评项目，只写自己的原始审计文件；明确「不编数字」。
4. **等回报**：全部回来后，验证 JSON 可解析、维数齐、总分能在 30 秒内复算。
5. **抽查复算**：随机抽 2 份提示词重新计量，与评审报的数必须一致。
6. **出报告**：按第八节的目录结构落盘。
7. **归档**：原始 JSON 与提示词**不要删**，下次做版本漂移对比要用。
8. **记录漂移**：新结果与基线逐维对比，变化超过 1 分的维度必须解释原因。

## 十一、已知坑（踩过一次，别再踩）

1. **数据库行对象没有 `.get()`** —— 拿到行先转成字典再取字段。
2. **换行符混写会毁掉文件**：写回文本时统一用一次性写全文件的接口，别用会自作主张转码的命令。
3. **PDF 生成库的段落是 XML**：所有动态文本必须转义，否则 `<` 会被当标签、`&` 会炸。
4. **表格里别放裸字符串**：中文会掉成方块。中文一律走段落对象。
5. **端口是静默杀手**：端口号写错 = 零报错零消息，小白永远查不出来。
6. **离线估算对中文高估严重**（本次最高 +73%），别拿它估成本。
7. **mock 环境会掩盖真实行为**：mock 下「没 key」不报错，功能结论要在真 key 下验。
8. **没有 CI 的项目，别把「测试通过」当默认**：先确认测试脚本存在。
